# Builder-Baseline: native build of the authors' published tuttekiri code as a referee baseline

Output: baseline/native/ (CMake project wrapping baseline/tuttekiri/code/cpp), a CLI `tuttekiri_cli`, and baseline/README.md. Do NOT modify anything inside baseline/tuttekiri/ (treat it as read-only upstream); copy or reference its sources from a sibling directory.

Read first: specs/common_preamble.md; code/README.md (our JSON graph contract); baseline/tuttekiri/README.md; baseline/tuttekiri/code/cpp/ (all files: utils/Hmesh, coloring/*, geometry/{kirigami,deployment,unit_pattern}, opt/{opt,deployment,prevent_intersections,fully_closed}, parameterization/*, bind.cpp for the API surface the web app calls).

Goal: a native (arm64 macOS, clang) executable that runs the AUTHORS' implementations of: face-orientation assignment (coloring/*), hole/constraint construction + Tutte auxetic embedding solve (their Eq. 4/6 equivalents), shape-space basis, forward deployment, and the collision-prevention optimization (opt/prevent_intersections = their Eq. 9), and fully_closed optimization — on OUR JSON graphs, writing results in OUR JSON conventions so they can be compared 1:1 with code/src/core.

Steps:
1. Dependencies: libigl v2.5.0 and Optiz (github.com/segaviv/optiz) are pulled by their CMake via FetchContent — cloning public repos is allowed (nothing leaves the machine). Eigen: prefer /opt/homebrew/include/eigen3 (Eigen 5.0.1) if it compiles; if their code needs 3.4, let FetchContent fetch it. Strip the emscripten link options and bind.cpp; add your own main.cpp.
2. Mirror bind.cpp's exported functions: read what the web UI calls (sequence of calls for load → color → solve → basis → deploy → prevent intersections → fully closed) and replicate that sequence in the CLI with subcommands: `color`, `solve` (particular solution + null basis), `deploy --theta`, `prevent` (their collision optimization, with their default parameters AND a parameter sweep option), `closed`. Input: our JSON (vertices, faces, optional orientation, optional periodic). Output: JSON with vertex positions, σ, hinge/split edge lists, holes, basis, θ_max as THEY compute it (find their deployment-range routine), and timings.
3. Parity tests (write to baseline/parity.md): on our 8 reference cases (results/core_validation/cases/*/ inputs) compare: σ (allow global flip), E_hinge/E_split sets, number of holes, rank/dim of shape space, particular solution after their projection vs ours (up to null-space ambiguity: check residual of ours in THEIR constraint system and vice versa), FK positions at θ=30° (after rigid alignment), and θ_max. Report every mismatch with numbers; do not paper over. Also run their `prevent` on snub_square and truncated_square_488 with their defaults and record the achieved θ_max (ours got 1.646 and 2.027-at-best; see results/core_validation/reference_cases.md).
4. Document exact build commands. If something cannot be built natively (e.g. a hard emscripten dependency), isolate the smallest subset that can (at minimum: coloring + constraint solve + deployment) and say precisely what is missing.
Do not commit. Reply with: build status, the parity table, and the baseline θ_max numbers.
